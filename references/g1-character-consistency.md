# G1 — 角色立绘一致性方案（L0 四宫格参考卡 + 模型适配的参考接入法）

> 本文件是 `avg-game-maker` skill 的配套文档，对应 8 步流水线里**「第 5 步资源核对 / 出图」**这一环里
> 最关键的"角色不串脸"工作流。图片资产（背景 + 立绘）走 ComfyUI 出图，但**角色长相一致**不能只靠
> 提示词——必须靠一套**权威参考资产（四宫格基准卡 L0）+ 与模型架构匹配的参考接入法**。
>
> **⚠️ 接入法取决于模型架构（见 §9）：**
> - **z-image-turbo / AuraFlow 系**：IP-Adapter 不兼容（节点无 AuraFlow preset），用 **img2img 初值法**
>   （裁 L0 单格当生成初值，denoise≈0.55–0.7，配合锁死文本描述锚定身份）。
> - **SDXL / FLUX 系**：可用标准 IP-Adapter（cubiq `ComfyUI_IPAdapter_plus`）或 FLUX Redux。
> - 本文件以 z-image-turbo 为默认模型；若换模型则切换到对应的 §9 子节。
>
> 关联文档：
> - 出图执行与云端坑见 `SKILL.md` 的 "Asset Generation" 一节 + `references/engine-conventions.md`。
> - 引擎图片资源登记（sprites/backgrounds）见 `references/engine-asset-catalog.md` 的 H 类。
>
> **本方案替换旧方案**：早期某 AVG 项目用过"先 4 张定调参考图 → 再批量 pose"的方法。其缺陷在于 4 张
> 定调图彼此可能不一致（脸型/发色/画风微差），导致 IP-Adapter 收到的参考信号本身在"漂移"。本方案用
> **1 张四宫格基准卡 = 1 个统一参考源** 解决根因，旧方案废弃。

---

## 0. 为什么需要这套方案（问题陈述）

AVG 游戏里同一个角色要出几十上百张立绘（不同 pose × 不同表情 × 不同场次）。纯提示词生图，每次
都是"重新想象"这个角色，结果：脸型变、发色变、服饰细节变 → **串脸**。

业界标准解法：先出 **1 张权威参考图**，把它的图本身作为 IP-Adapter 的参考输入，后续所有该角色的出图
都"照着这张画"。关键前提是**参考源必须稳定且唯一**——这就是本方案的全部用意。

---

## 1. 核心思路：每角色 1 张权威基准卡（L0）

所有后续出图的**参考源**都来自这张基准卡，从根本上消除"参考源不一致"的根因。
基准卡采用**四宫格单画布**（脸特写 | 正面全身 | 侧面全身 | 背面全身），白底、无裁切、比例标准——
一次生成 = 同一角色的四视图，天然互一致。

> **📌 标准步骤（强制）**：**出人物资产图的第一步，就是为每一个角色生成其 L0 四宫格参考卡。**
> 没有 L0，就不允许进入该角色任何立绘（pose / 表情 / 服饰变体）的出图。这是整套一致性方案的
> 前置硬门槛——L0 锁定后，后续所有该角色的出图都以它为参考源（img2img 初值或 IP-Adapter，见 §9）。

> **L0 的两种用法（按模型架构选一种，见 §9）：**
> - **z-image-turbo（默认）**：裁出某一格（通常是正面全身或脸特写）当 **img2img 初值**，
>   KSampler `denoise` 设 0.55–0.7 让模型从初值"长"出新姿势。初值含脸 → 身份被锚定。
>   **防脸忽手法**：交付用 L0_clean 只保留第 1 格主脸、抹掉其余 3 格的脸部
>   （避免多张脸互相干扰），但 img2img 初值仍使用未抹脸的单格原图。
> - **SDXL / FLUX**：整张 L0 或其裁格作为 **IP-Adapter / Redux 参考图**输入。

在基准卡之上，按游戏需求追加辅助层（表情集 L1、服饰变体 L2），形成**三层参考资产体系**。

---

## 2. 三层参考资产体系

| 层级 | 内容 | 用途 | 必要性 |
|------|------|------|--------|
| **L0 基准卡** | 四宫格：脸特写 \| 正面全身 \| 侧面全身 \| 背面全身，白底单画布 | **所有** pose/expression 出图的参考源（img2img 初值 或 IP-Adapter 输入，按模型架构） | **必做，每角色 1 张** |
| **L1 表情集** | 同一角色脸部的多表情排列（happy/sad/angry/surprised/shy…），保持脸型/发型/服饰一致 | 出表情立绘时的辅助参考（防止表情变形后脸变了） | **强烈推荐，每角色 1 张** |
| **L2 服饰变体包** | 同一角色穿不同服装的正面/侧面（校服/便装/制服/礼服…） | 多场景游戏需要换装时 | **按需，有换装才做** |

> **关键约束（剧本驱动，见 §6）**：L0 可在故事定稿后（Step 1/2 之后）就做；但 **L1、L2、最终批量立绘必须等
> 剧本分镜拆完、需求汇总后才出**，避免出一堆剧本用不到的废图。

## 2.5 S0 — 风格探索与模型选型实验（**本方案第 0 步，先于 L0**）

> **核心认知**：出图的**流程**是固定的（L0 → L1 → L2 → 批量立绘，与题材无关）；
> 但**每个故事的美术风格不同 → 适配的模型不同、提示词不同**。
> 上一部游戏的风格词**绝不直接套到新游戏**——这是画面风格漂移的头号原因。
> 因此正式出 L0 之前，必须先跑完 S0。

### S0.1 风格定义（继承 Step 1 设计骨架）

| 项 | 内容 |
|---|---|
| 输入 | Step 1 骨架的「美术风格 / 情感基调 / 题材」字段 |
| 产出 | **风格关键词表**：主体画风 / 线条 / 上色方式 / 光影 / 镜头语言 / 禁忌项 |
| 要求 | 风格词必须**具体可执行**。「日系二次元」太泛，模型会自由发挥；要写成「赛璐璐上色 + 细墨线 + 高调柔光 + 低饱和」这种能直接进 prompt 的颗粒度 |

### S0.2 模型选型实验（横向对比，必做）

| 项 | 内容 |
|---|---|
| 候选 | z-image-turbo（默认）/ SDXL 系 / FLUX 系 / 其他（见 §9 各架构的参考接入法） |
| 方法 | **固定同一组测试 prompt**（1 张 L0 四宫格 + 1 张场景背景）+ **同一 seed**，在每个候选模型上各跑一遍 |
| 判定维度 | ① 风格契合度 ② 角色一致性稳定性 ③ 多格布局遵循度 ④ 出图速度与成本 |
| 产出 | **选型结论表**（模型 + 胜出理由 + 落选原因），锁定 **1 个主模型** |
| 红线 | 用**小尺寸廉价快筛**，不要拿正式资产去试错；实验结论未锁定前不出 L0 |

> 选型结论要连同样图一起存档——下一部游戏如果风格相近，可直接复用结论跳过实验。

### S0.3 风格提示词块沉淀（Style Block）

把 S0.1 的风格词 + S0.2 验证有效的表述，固化成 **3 段可复用文本块**：

| 块 | 内容 | 示例 |
|---|---|---|
| `STYLE_POSITIVE` | 画风 / 线条 / 上色 / 光影 / 质感 | `赛璐璐上色，细墨线，高调柔光，低饱和…` |
| `STYLE_NEGATIVE` | **该风格要排除**的东西 | 写实风要排除 `二次元，赛璐璐，扁平色块`；二次元风要排除 `照片，真实皮肤纹理` |
| `STYLE_PARAMS` | 该风格在该模型上的参数 | `steps=8, cfg=1, 2048×1024`（随模型/风格变化） |

**之后所有出图提示词统一构成**：

```
最终 prompt = STYLE_POSITIVE + <主体描述：角色/场景/构图> + <负面用 STYLE_NEGATIVE + 通用负面>
```

L0 / L1 / L2 / 背景 / 批量立绘**全部套同一套 Style Block**，这是全局画风统一的机制保障。

### 风格差异的连锁影响（思考触发器，非硬映射）

| 维度 | 纯情治愈 | 恐怖 | 悬疑 | 奇幻 |
|---|---|---|---|---|
| 画风词 | 水彩 / 清新通透 | 厚涂 / 颗粒噪点 | 写实 / 冷峻 | 油画 / 华丽装饰 |
| 光影 | 高调柔光 | 低调高对比、硬阴影 | 冷调低饱和、局部打光 | 戏剧性光、辉光 |
| 线条 | 细柔 | 粗糙抖动 | 硬朗简洁 | 繁复华丽 |
| 禁忌词差异 | 排除暗黑、血腥 | 排除明亮可爱、暖色 | 排除高饱和、活泼 | 排除现代元素、写实照片感 |
| 模型倾向 | 以 S0.2 实测为准，不预设 | | | |

> 上表**仅用于打开思路**，实际以 S0.2 实验结果为准——模型能力会变，别拿表当结论。

### 三条纪律

1. **换风格 = 重跑 S0**，不要中途换风格词。
2. **禁止混用两套 Style Block**（上一部 + 这一部），混用必漂移。
3. S0 未完成，**不进 L0**。

### 产出物

`<project>/story-wip/素材/style_block_<game>.md`：Style Block 三段 + 选型结论表 + 实验记录（模型 / seed / 尺寸 / 结论 / 样图路径）。

## 3. L0 基准卡规范（核心标准）

### 3.1 画布规格
- 分辨率：**宽 2048 × 高 1024（2:1 横幅）** — 在 z-image-turbo 上实测为可稳定出「面部特写 + 正面 + 侧面 + 背面」四格的最优比例（**已验证 v7：seed=20260833 成功**）。
  - 早期试过 2560×960（出 ~5 个角色）、1024×2048（出 ~3 个），均不稳定；**2:1 横幅对多角度排列遵循度最高**。
- 背景：纯白 `#FFFFFF`，无环境、无道具。
- 排列：`[面部大特写] [正面全身] [左侧面全身(profile)] [背面全身]`（第 1 格为脸部占满面板的特写；第 3 格为 90° 侧影）。
- 要求：从头到脚无裁切、比例标准、构图工整。

### 3.2 通用提示词模板（填空式，已验证可稳定出 4 格含侧面）

> **2026-08-30 实测（z-image-turbo，画布 2048×1024）**：以下模板实测可稳定输出
> 「面部大特写 / 正面 / 左侧面(profile) / 背面」四格。关键点：① 开头的**全局角度约束**
> 「四个面板必须从四个截然不同的角度…禁止重复角度」；② 侧面用 **"严格90度左侧面全身（profile view）"** 强描述
> —— 这两点是 v1→v7 反复试错后侧面才稳定出现的原因。
>
> **⚠️ 这是模板不是定稿**：`{外貌/体型/服饰}` 三段必须按**每个角色的实际设定**替换；整段的画风词
> （"二次元插画 / 水手服 / 日系清新"等）也随**每个故事的美术风格**调整。格式与颗粒度可复制，内容必须定制。

```
【角色设定参考图，一张画布内】四个面板必须从四个截然不同的角度展示同一个角色，禁止重复角度。
最左侧独立面部大特写，脸部占满整个面板，只展示五官、脸型、发型、发色，无肩颈躯干；
右侧第1格正面全身站立（face front），第2格严格90度左侧面全身（profile view，身体完全侧向，仅展示一侧脸颊与鼻梁线条，与正面格角度截然不同），第3格背面全身（back view），
从头到脚完整展示人物，无裁切，纯白色背景，构图工整规整，专业角色设计稿，人物比例标准。

{角色外貌描述段 — 发型/发色/眼睛/脸型/肤色}，
{角色体型描述段 — 身高感/体态/年龄感}，
{角色服饰描述段 — 服装细节/配色/材质}，
双手姿态自然，肌肤白皙细腻，
柔和干净的漫射光影，高级柔和氛围感，干净通透色彩，
8K超高细节，精致二次元插画，线条干净。
```

### 3.3 通用负面提示词（必加，防崩坏）

```
人物截断，裁切不全，畸形四肢，扭曲手部，多手指，残缺肢体，
杂乱背景，水印，文字，污渍，强烈阴影，昏暗，杂乱构图，
多余装饰，道具，环境景物，low quality, blurry, deformed
```

## 4. L1 表情集规范

### 4.1 画布规格
- 竖幅或横幅均可，建议 **6–8 个表情网格排列** 在一张画布上、独立区域清晰分隔。
- 同一角色、同一角度（通常正面或微侧）、同一服饰，**仅改变表情**。

### 4.2 推荐覆盖表情（按 AVG 常用度排序）

| 优先级 | 表情 | AVG 典型场景 |
|--------|------|-------------|
| P0 | default（平静/微笑） | 日常对话默认 |
| P0 | happy（开心/大笑） | 欢快场景 |
| P0 | sad（悲伤/低头） | 悲伤/离别 |
| P1 | surprised（惊讶） | 突发事件 |
| P1 | angry（生气/严肃） | 冲突/争执 |
| P1 | shy（害羞/脸红） | 告白/暧昧 |
| P2 | thinking（思考/疑惑） | 谜题/抉择 |

> **不要铺满 7 个**：只出剧本需求表（见 §6）里实际用到的表情，省成本、也避免用不到的表情分散参考信号。

### 4.3 提示词模板

```
【CG二次元角色表情参考集】同一角色的多个面部表情变化集合，
排列在一张画布上，纯白色背景，每个表情独立区域清晰分隔。
保持完全一致的{脸型/发型/发色/眼色/服饰}，仅改变面部表情和眼神。

{同 L0 的角色外貌+服饰描述}

表情列表：平静微笑 / 开心大笑 / 悲伤低头 / 惊讶睁眼 / 生气皱眉 / 害羞脸红 / 思考疑惑
柔和干净漫射光，8K超高细节，精致二次元插画，线条干净。
```

## 5. L2 服饰变体包（按需）

当游戏有多套服装（校服/私服/运动服/礼服/战斗服…）时：
- 每套服饰至少 **正面 + 侧面** 两张；或合并为类似 L0 的四宫格但替换服饰。
- 提示词在 L0 基础上**只改 `{服饰描述段}`**，其余不变，保证人还是同一个人。
- 仅在剧本确有换装场景时才做（见 §6 的裁剪判定）。

## 6. 剧本驱动的生产流水线（核心执行顺序）

> 这是本方案最关键的一条规则：**先有剧本，再反推立绘需求，最后出图。**

```
Phase 1 — 角色基准（故事定稿后，Step 1/2 之后即可做，不依赖剧本分镜）
  A. 角色设计表（文本）：外貌/性格/服饰/色调，用户确认
  B. L0 基准卡生成 + 锁定  ← **【标准第一步】这是"能画该角色任何立绘"的前置条件，必做、每角色 1 张**
                            （模板见 §3.2 / 已验证范例见 §3.4；画布 2048×1024）

Phase 2 — 剧本驱动的需求汇总（Step 3 剧本化 → Step 4 拆资源）
  C. 通读剧本每个分镜，逐幕标注：出场角色 / 位置 / 动作 / 表情 / 场景
  D. 聚合为《立绘需求总表》：角色 × 姿势 × 表情 × 出现场次 × 数量
  E. 据表判定：需要哪些 L1 表情集、哪些 L2 服饰变体（不用的不生成，省成本）

Phase 3 — 立绘生成（Step 5 核对前）
```

## 9. 参考图接入策略（按模型架构分）

> ⚠️ **2026-08-30 实测结论**：z-image-turbo 是 AuraFlow/SD3 系 Rectified-Flow 模型，
> cubiq `ComfyUI_IPAdapter_plus` 的 `IPAdapterUnifiedLoader` 仅支持 SD1.5/SDXL preset，
> **不支持 AuraFlow**。`ReferenceLatent`（edit-model 专用）也不适用于普通 txt2img 基模。
> 因此 z-image-turbo 的角色一致性必须走 **img2img 初值法** 或 **ControlNet**。

### 9-A — z-image-turbo / AuraFlow 系（默认，已验证可用）

**方法：img2img 初值法**（零额外权重、任何基模通用）

| 步骤 | 操作 | 节点/参数 |
|------|------|----------|
| ① 出 L0 | **一次性 4 宫格 txt2img**（画布 2048×1024，模板见 §3.2/§3.4） | 复用 z-image-turbo 管线，改 prompt + size；单 pass 出四视图，一致性优于分图拼 |
| ② 去脸（用户手动） | 一次性布局不稳定（常出 5 个角色而非严格 4 等分），**自动按等分抹脸会错位** → 交付用户用画图/Photoshop **白笔涂掉非主脸区域的面部** | 脚本不再自动抹（见 `gen_l0_onepass.py` 已移除自动抹脸） |
| ③ 选初值格 | 从 L0_raw 裁出一张单格（推荐正面全身或脸特写）作为 img2img init | PIL crop |
| ④ 上传参考 | `POST /upload/image` 上传裁出的单格 → 得到 uploaded_name | ComfyUI API |
| ⑤ 搭 img2img wf | LoadImage(uploaded) → VAEEncode(vae, ref) → KSampler(latent_image=ref_latent, denoise=0.55~0.7) | 替换 EmptySD3LatentImage 为 VAEEncode 输出 |
| ⑥ 锁文本 | positive prompt 必须包含完整角色描述（发色/瞳色/服饰/体型），与 L0 一致 | CLIPTextEncode |
| ⑦ 出图 | KSampler steps=8, cfg=1, sampler=res_multistep, scheduler=simple | 同 bg 出图参数 |

**denoise 参数指南**：
- `0.55–0.60`：强锚定（姿势变化小，脸最稳）→ 用于表情变体
- `0.65–0.70`：中等锚定（姿势可大变，脸基本保持）→ 用于不同 pose
- `>0.75`：弱锚定（接近纯 txt2img，身份可能漂移）→ 不推荐

**ControlNet 增强路径（可选，需权重文件）**：
云端有 `ZImageFunControlnet` 节点（专为 Z-Image 的 ControlNet）。若 `/workspace/ComfyUI/models/controlnet/`
下存在 z-image 专用的 controlnet 权重（如 `z-image-controlnet.safetensors`），可在 img2img 基础上叠加：
```
LoadImage(ref_crop) → ZImageFunControlnet(model=UNET, control_model=controlnet_weight,
                                          image=ref_crop, strength=0.6~0.8)
→ Apply to KSampler 的 additional_inputs
```
这给**结构一致性**（pose/composition 额外约束），与 img2img 的**身份锚定**互补。
**若没有 controlnet 权重则跳过**，仅用 img2img 已足够。

### 9-B — SDXL 系（备选方案）

若未来切换到 SDXL 基模（如 `sd_xl_base_1.0.safetensors`），可用标准 IP-Adapter：

| 组件 | 文件名（UnifiedLoader 要求的精确命名） | 放置目录 |
|------|-------------------------------------|---------|
| IP-Adapter 权重 | `ip-adapter_sdxl.safetensors` | `models/ipadapter/` |
| CLIP-Vision 模型 | `CLIP-ViT-H-14-laion2B-s32B-b79K.safetensors` | `models/clip_vision/` |

节点接线：`IPAdapterUnifiedLoader(model=UNET, preset="STANDARD")` → `IPAdapterApply(image=L0_ref)` → 接入 KSampler。

### 9-C — FLUX 系（备选方案）

FLUX 有原生参考机制（Redux / FLUX IP-Adapter），一致性更强但需 FLUX 基模 + 对应权重。
节点：`ReduxAdvanced` / `FluxKontextMultiReferenceLatentMethod`。

### 9-D — 存储目录规范

| 内容 | 路径 | 说明 |
|------|------|------|
| L0 四宫格（原始） | `{game}/ref/{char}_L0_raw.png` | 未处理，含全部 4 视图 |
| L0 四宫格（交付用） | `{game}/ref/{char}_L0_clean.png` | 抹掉 3 视图脸部后的版本 |
| L0 单格（img2img 初值源） | `{game}/ref/{char}_L0_front.png` 等 | 裁出的单格原图 |
| 最终立绘 | `{game}/sprites/{char}_{pose}.png` | 引擎 sprite 目录 |

> 其中 `{game}` = 游戏统一前缀（如 `sakura`），`{char}` = 角色 id（如 `alice`）。

### 9-E — 一致性验收标准

什么叫"串脸了"需要返工？逐项比对 L0 主脸 vs 新立绘的脸部：

| 要素 | 判定标准 | 返工阈值 |
|------|---------|---------|
| 发色 | RGB 差 < 30（目测同色系） | 完全变色 → 重出 |
| 瞳色 | 同上 | 同上 |
| 脸型轮廓 | 整体形状一致（圆脸不变成尖脸） | 明显变形 → 重出 |
| 服饰细节 | 领结颜色/裙褶数量一致 | 关键特征丢失 → 重出 |
| 画风/线条粗细 | 与背景风格协调 | 与背景割裂感强 → 调整 prompt |

> **验收流程**：S2 预检 3 张 → 全部通过才批量；批量后抽检 10%，不合格率 >20% 则整批重调参数。

### 9-F — 构图尺度一致性（**容易被漏掉、但换图时会肉眼可见地崩**）

上面 9-E 管的是"脸像不像"，还有一类偏差**根本不看脸**：**人物在画布里的大小 / 位置**。
同一角色的不同 pose 若构图尺度不一致，切图时角色会**突然变大或变小**，非常出戏。

**规范（实测标定）**：用 alpha 通道量**轮廓最上面一行**占画面高的比例，记作 `top%`。

| 指标 | 规范 | 含义 |
|---|---|---|
| `top%` | **3.5% ~ 10%** | 头顶离画面上缘的距离占比。超出 → 头被放大/缩小 |
| `bottom%` | ≈ 99.9% | 人物应当**顶到下缘**（被画框裁断），否则会出现"悬浮半身像" |

> 本作 20 张已落位立绘实测：`top%` 分布 3.5（陆昭 default）~ 10.0（江砚 tense），无一例外。

**量测工具**：`素材/measure_sprite_frame.py`（alpha 通道，逐张打印 top%/bottom%/宽%）。

🔴 **两个"把人物画大"的系统性成因**（都踩过，详见 `krea2-persona-sheet` §11.7）：
1. **量测源用错**：在浅灰底稿上用"亮度阈值"找轮廓，会**漏检浅色头发**
   （白发/银发 ≈ 浅灰背景）→ `head_pct` 虚高 → 提示词把人物写低 → 输出 `top%` 翻 3 倍。
   ✅ **一律优先用已抠图 RGBA 的 alpha 通道量人物**，灰底稿+亮度只作兜底。
2. **"只有一颗头"的参考图会让模型照搬其构图** → 大头特写。
   ✅ 构图段里必须加守卫：「参考图只是头像、不代表构图，不要头肩特写，人物从头到腰部以下完整入镜」。
   ✅ 另外：`outfit` 描述里**要提下半身**（只说上半身时模型更容易只画上半身）。

> **元教训（值得单独记住）**：出图不合格时，**先量数字、再猜原因**。
> 这一轮如果只靠"看图觉得头大了"去反复改提示词，大概率还在原地打转；
> 是 `measure_sprite_frame.py` 给出的 `top% = 25.8 vs 规范 3.5~10` 把问题钉死的。

## 10. 立绘抠图：透明背景（色键 Matte，G1 附属小节）

> 适用：任何需要「透明背景立绘 / 物件图」的 AVG 项目。
> 前置：读 `g1-character-consistency.md`（出图一致性）；本步只解决**出图之后怎么变透明**。

### 10.1. 定位与核心认知

**抠图不是在出图之后才想办法，背景色必须在出图阶段就为抠图规划好。**
这是整套流程能成立的前提——出图提示词里写什么背景，决定了后面能不能干净分离。

当前方案 = **纯 PIL 色键，零依赖、零外部服务**（不联网、不需模型权重）。

### 10.2. 为什么不用 AI 抠图（现状 + 暂缓升级项）

#### 10.2.1 已实测失败的方案（2026-09，CloudStudio 云端 + 本地双线验证）

| 方案 | 失败原因 |
|---|---|
| BiRefNetRMBG / RMBG 节点 | TF checkpoint 加载报错 |
| easy imageRemBg | HuggingFace 401（无凭证） |
| mtb 节点组 | 直接把 ComfyUI 实例搞成 500 |
| 本地 rembg / onnxruntime | PyPI 源被掐，装不上 |
| FaceID + ControlNet（锁脸用） | 节点在，但缺权重文件 |

**结论：本环境下 AI 抠图暂时走不通，色键是当前唯一可用路径。**

#### 10.2.2 🟡 暂缓升级项：AI 抠图（P1，将来做）

- **判断**：AI 抠图（RMBG-2.0 / BiRefNet / MODNet）对**发丝、半透明边缘、细小装饰**的精细度
  明显高于色键。色键在「白发 / 毛领 / 飘带 / 半透明薄纱」这类高频细节上会啃边或残留。
- **现状**：受模型权重与环境限制，暂时放置。
- **触发重做的条件**（满足任一即可重启）：
  1. 云端实例预装了 RMBG / BiRefNet 权重，或能访问 HuggingFace；
  2. 本地能装上 `rembg` + `onnxruntime`（有可用 PyPI 源）；
  3. 项目出现「色键不擅长的素材」（白发飘散、毛绒、半透明）。
- **重做时的做法**：保留 `matte_*` 色键函数作为**兜底与 A/B 对照**，
  AI 抠图结果同样要过 §5 的质检（四角 alpha / 残留统计），二者取优。
- **注意**：AI 抠图换掉的是「判据」，不是「后处理」——连通域约束、收缩羽化、despill 仍然要保留。

### 10.3. 出图阶段：背景色怎么定

立绘出图提示词里固定附加一段（中文，Krea2 对中文响应更好）：

```
背景为均匀的纯青色背景（cyan，明亮的青蓝色），
背景颜色完全均匀一致、无渐变、无纹理、无阴影、无杂物。
```

⚠️ **Krea2 有时会无视背景提示**（实测 9 角色中江砚一次直接给了浅灰白底 233–241）。
→ 出图后**必须先看背景色再决定用哪个模式**，见 §6 的自动判断。

### 10.4. 四代方案演进与死因（决策依据，别走回头路）

| 代 | 背景 | 判据 | 死因 |
|---|---|---|---|
| 1 | 中灰底 | 逐通道接近底色 + 低饱和 | 撞白发（180–230）**和**灰衣（140） |
| 2 | 中灰底 | 上条 + 局部纹理 MAD 低 | 救回毛发，灰衣仍中招 |
| 3 | 绿幕 | g − max(r,b) > T | Krea2 无视绿幕，照给灰白底 |
| **4** | **青幕** | **g − r > 20 且 b − r > 20** | ✅ 现役 |

**为什么灰阶必死**：白发（180–230）与黑衣（30）分处亮度两端，任何灰阶亮度都会撞其中之一——
中灰撞白发+灰毛衣，深灰撞黑衣，无解。

**为什么青幕能成**：判据从「亮度」换成「色相」。
色相与明暗无关 → 天然容忍背景光照渐变（用亮度差判据时会出现残留斑块）。
所有人物元素（白发 / 灰衣 / 黑衣 / 藏青 / 棕色 / 白人肤色）的 `g − r` 都在 −10～+5，
青幕在 +60，**中间隔着 55 的安全间隔**。唯一禁忌：**青/绿色衣物**（会一起被抠掉）。

### 10.5. 青幕算法（现役，`matte_cyan`）

```python
def matte_cyan(src, out_alpha, out_preview, HUE_T=20, soft=0.8, shrink=4, despill=True):
    im = Image.open(src).convert("RGB"); W, H = im.size
    ro, go, bo = im.split()

    def over(ch, base, t):                      # ch - base > t（负值自动截 0）
        return ImageChops.subtract(ch, base).point(lambda v: 255 if v > t else 0)

    bgmask = ImageChops.multiply(over(go, ro, HUE_T), over(bo, ro, HUE_T))
    bgmask = bgmask.filter(ImageFilter.MedianFilter(3))   # 去噪
    bgmask = bgmask.filter(ImageFilter.MaxFilter(3))      # 膨胀保连通

    # ★ 只保留与画布四边连通的背景：人物内部破洞自动填回
    fill = bgmask.copy(); seeds = []
    for x in range(0, W, 4): seeds += [(x, 0), (x, H - 1)]
    for y in range(0, H, 4): seeds += [(0, y), (W - 1, y)]
    for p in seeds:
        if fill.getpixel(p) > 128: ImageDraw.floodfill(fill, p, 128, thresh=0)
    outer_bg = fill.point(lambda v: 255 if v == 128 else 0)

    alpha = ImageChops.invert(outer_bg)
    for _ in range(max(0, shrink // 2)):
        alpha = alpha.filter(ImageFilter.MinFilter(3))    # 收缩，啃掉边缘描边
    if soft > 0: alpha = alpha.filter(ImageFilter.GaussianBlur(soft))

    out_im = im
    if despill:                                  # 去青溢：r = max(r, min(g,b))
        r2 = ImageChops.lighter(ro, ImageChops.darker(go, bo))
        out_im = Image.merge("RGB", (r2, go, bo))

    out = out_im.convert("RGBA"); out.putalpha(alpha); out.save(out_alpha)
```

四步要点：
1. **判据** `g − r > 20 且 b − r > 20` → 背景掩膜
2. **连通域约束**：从画布四边种子 floodfill，只保留与边框连通的背景
   ——人物衣服上被误判的小破洞在内部、不连通 → 自动填回；臂间缝隙上下开口 → 仍正确抠掉
3. **收缩 + 羽化**：`MinFilter` 收 ~2px 啃掉描边 → `GaussianBlur(0.8)` 抗锯齿
4. **despill**：`r = max(r, min(g,b))`，边缘不再泛青

### 10.6. 五种模式与选择（CLI 前缀）

| 前缀 | 模式 | 适用 |
|---|---|---|
| `c:` | `matte_cyan` | **首选**，青幕底 |
| `l:` | `matte_light` | 浅灰白底兜底（Krea2 无视背景提示时）|
| `g:` | `matte_green` | 绿幕底（Krea2 常无视，成功率低）|
| `t:` | `matte_tex` | 灰底 + 加纹理判据 |
| — | `matte` | 灰底基础色键（最容易撞色）|

`matte_light` 要点（浅底兜底）：**判据 = 与四角采样底色的逐通道差 < 26 + 低饱和**，
不是绝对亮度阈值——底色常有暗角/渐变，固定亮度阈值会在画布角落漏判、留下白线。
风险：白色/米白衣物、银白发会与浅底撞色，这类必须重出青幕版。

### 10.7. 质检（必做，别只看缩略图）

1. **数值体检**：四角 alpha 必须 = 0；边框环带均值 < 50；透明占比 36–52%（半身立绘）。
   ```bash
   python check_matte.py          # 打印 tag / size / corners / ring / trans% / opaque%
   ```
   判定：**四角 255 + opaque 100% = 完全没抠掉**，直接回 §6 换模式。
2. **三联对比图**：出图原图 → 抠图结果（棋盘格=透明）→ 贴游戏深底色（模拟实际效果）。
3. **残留诊断图**：把「alpha>200 且明显是背景色」的像素标红，占比 < 0.2% 可接受；
   集中成线就要处理。

### 10.8. 踩坑清单

- **出图后必开图 + 看体积**：5–6KB = 单色空图，ComfyUI history 照样报 success。
- **别用「逐通道亮度差」判青幕**：背景有渐变时会漏判 → 残留斑块。
- **改判据语义时必须同步改默认参数**：曾把 `L_T` 从「绝对亮度 226」改成「差值 26」
  却漏改默认值，一波抠掉 94% 人物。
- **「提交成功却抓不到产物」→ 直接查 `/history` 里该 pid 的 `status.messages`
  找 `execution_error`**（看 `node_id` / `exception_message`），比反复重试快得多。
  `execution_cached` 全命中 = 采样没问题，故障只在落盘（常见 `[Errno 122] Disk quota exceeded`）。
- **临时试验图记得清理**，别让它混进交付目录。

### 10.10. 与 Step 4/5 的衔接

- 立绘透明图落位 `public/images/characters/`，在 `manifest.ts` 的 `sprites[charId][poseKey]` 登记
